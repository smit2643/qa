# Architecture Overview

## System Design

Two deployable services sharing PostgreSQL, Redis, and MinIO:

```
┌──────────────────────────────────────────────────────────┐
│                  FRONTEND (Next.js 14)                   │
│            Tailwind CSS + shadcn/ui + React Query        │
└─────────────────────────┬────────────────────────────────┘
                          │ REST / WebSocket
┌─────────────────────────▼────────────────────────────────┐
│                BACKEND API (FastAPI/Python)               │
│                                                          │
│  auth  │  projects  │  ai  │  jobs  │  reporting         │
│  billing  │  notifications                               │
└──────┬────────────────────────────┬───────────────────────┘
       │ PostgreSQL                 │ Redis (Celery broker)
┌──────▼──────┐         ┌───────────▼──────────────────────┐
│  PostgreSQL │         │     TEST RUNNER (Python/Celery)   │
└─────────────┘         │  playwright-python + browser-use  │
                        └──────────────────────────────────┘
┌─────────────┐
│    MinIO    │  ← videos, logs, traces, screenshots
└─────────────┘
```

## Service Responsibilities

### Frontend (`/frontend`)
- Next.js 14 App Router
- All user-facing UI: dashboard, projects, test editor, run viewer
- Communicates with backend via REST + WebSocket for live run status

### Backend API (`/backend`)
- FastAPI modular monolith
- All business logic except browser execution
- Pushes test jobs to Redis queue
- Receives results from runner workers via internal PATCH endpoint

### Test Runner (`/runner`)
- Celery workers consuming from Redis
- Executes Playwright tests in isolated browser contexts
- Records video per test run (Playwright built-in)
- Uploads artifacts (video, logs, HAR) to MinIO
- Calls backend `/ai/heal` on selector failure (self-healing)

## Data Flow: Test Execution

```
1. User clicks "Run Suite" (or CI webhook hits /runs/trigger/ci)
2. Backend creates TestRun + TestResult rows (status=queued)
3. Backend pushes one Celery task per test into Redis
4. Runner worker picks up task
5. Worker launches headless Chromium via playwright-python
6. Test code (generated by AI) executes
7. Video + console logs captured; uploaded to MinIO
8. Worker POSTs result to backend: status, video_url, log_url, error
9. Backend updates TestResult row
10. If all results done → TestRun marked passed/failed
11. Notifications fired (Slack, email, GitHub status check)
```

## Data Flow: AI Test Generation

```
1. User submits description + target URL
2. Backend ai/service calls browser-use agent
3. Agent visits target URL, reads accessibility tree
4. Accessibility tree + description sent to Claude (LLM)
5. Claude returns Playwright test code
6. Code stored in test_cases table
7. Test available to run immediately
```

## Data Flow: Self-Healing

```
1. Runner: Playwright throws "Element not found" on selector X
2. Runner calls GET /api/v1/ai/heal with {broken_selector, accessibility_tree}
3. Backend ai/service sends both to Claude
4. Claude returns corrected selector
5. Runner retries test with new selector
6. On success: backend updates test_cases.code with new selector
7. On failure after 2 retries: mark result failed + AI summary
```

## Database Schema (ERD)

```
organizations ──< memberships >── users
      │
      └──< projects >──< test_suites >──< test_cases
                                │               │
                                └──< test_runs >──< test_results
```

## Key Design Decisions

| Decision | Rationale |
|---|---|
| Modular monolith (not microservices) | Ship fast; extract modules only when load demands |
| Runner is separate service | Needs Playwright + heavy parallelism; isolated from API |
| browser-use for AI↔browser | Saves building the agent loop from scratch; multi-LLM |
| Accessibility tree (not pixels) | 10x more stable selectors than CSS classes or visual AI |
| Celery + Redis (not BullMQ) | Pure Python stack; no Node.js needed |
| MinIO → S3 | Cloud-agnostic; same boto3 API in both environments |
